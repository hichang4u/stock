## 3. PAPER 실측 기준선

**전부 PAPER 서버 기록이다. REAL의 지연이 아니다.**

시각의 뜻:

| 이름 | 무엇의 시각인가 |
|---|---|
| 선정 | `TARGET_LOCKED` 로그를 남긴 시각 |
| 접수 | `ENTRY_ORDER_SENT` 로그를 남긴 시각. 주문 응답을 받은 **뒤**다 |
| 전송 | 접수 − `network_ms`. 주문 호출의 지연 기록이 있을 때만 안다 |
| 체결 통보 | `FILL_NOTICE_RECEIVED` 로그를 남긴 시각 |
| 체결 확인 | `ENTRY_EXECUTED` 로그를 남긴 시각 |
| 개장 예정 | 같은 로컬 시계의 09:00:00. 그날 첫 체결 시각이 아니다 |

모든 차이는 같은 로컬 시계의 로그 시각끼리 뺀 것이다. 체결 통보의 거래소 시각(초 단위)과
로컬 시각의 차는 시계가 달라 계산하지 않았다.

## 4. 위험 초안 오프라인 평가

초안(coordinator 제안, 사용자 미확정): 거래당 계획 손실 0.10%, 일일 중단 0.30%, 고점 대비
낙폭 2.0%, 순손실 3연속 중단, 최초 주문 투입 상한 5%. **설정에 쓰지 않았고 분석
시나리오로만 적용했다.**

### 4.1 계산할 수 있는 것과 없는 것

`sizing.allowed_order`를 온전히 돌릴 수 없다. 없는 것:

- 승인 자본(절대액), 스트레스 손실률 구성요소, 절대 주문 상한
- 지정가 상한 이내 호가 잔량 — 로그에는 최우선 매도호가 한 단계의 잔량만 있다
- 참여율과 주문별 예상 거래대금, 주문별 계좌 자료 기준 시각

확정 필드 둘로 정해지는 것은 **자본 대비 주문 비율의 상한**뿐이다:
`min(5%, 0.10% ÷ 스트레스 손실률)`. 실제 허용 금액은 현금·절대 상한·유동성 때문에 이보다
작을 수 있고 클 수는 없다.

| 스트레스 손실률 (가정) | 자본 대비 주문 비율 | 결정 한도 |
|---|---|---|
| 2% — 손절 폭만. 설계가 금지한 기준선, 비교용 | 5.00% | 둘이 같다 |
| 3% | 3.33% | 손실 예산 |
| 4% | 2.50% | 손실 예산 |
| 6% | 1.67% | 손실 예산 |

스트레스 손실률이 2%보다 크기만 하면 투입 상한 5%는 걸리지 않는다. 주문 크기를 정하는
것은 손실 예산이다.

- **일일 중단선과 낙폭 한도는 이 이력에서 한 번도 작동하지 않는다.** 최악 거래가 계좌의
  0.19%(3% 가정)라 0.30%에 닿지 않고, MDD는 0.67%다. 초안에서 실제로 일하는 규칙은 손실
  예산(주문 크기)과 연속손실 중단이다.
- 계좌 누적이 작은 것은 주문 비율이 작아서다. **수익성이 좋아지거나 나빠진 것이 아니다.**
  거래당 손익률은 어느 행이든 같다.
- MDD는 청산 손익 기준이다. 보유 중 평가손실은 들어 있지 않다(거래 기록에 보유 중 저점이
  없다).

## 6. 프로세스 장애 검증 (합성)

임시 디렉터리의 합성 저장소와 **실제 별도 프로세스**로 봤다
(`tests/test_real_validation_process.py`, 일꾼 `tests/real_validation_proc_worker.py`).
자식 프로세스는 60초 안에 끝나지 않으면 죽이고 실패 처리한다. Windows 11, Python 3.12.10,
SQLite 3.49.1에서 7개 테스트 통과(8초). 운영 프로세스는 건드리지 않았다.

| 상황 | 결과 |
|---|---|
| 프로세스 6개가 같은 손실 예산을 동시에 예약 | 1개 성공, 5개 `LossBudgetExceeded`. 장부에 주문 1건 |
| 프로세스 6개가 같은 주문 번호로 동시에 예약 | 1개 성공, 5개 `DuplicateReservation` |
| 프로세스 6개가 같은 주문을 동시에 해제 | 1개만 해제, 나머지는 "이미 풀림" |
| 프로세스 6개가 같은 일일 중단을 동시에 해제 | 1개만 해제 기록, 중단 이벤트는 HALT·RESUME 한 쌍 |

관찰: 트랜잭션 중 종료 뒤 `gate.db-journal` 파일이 남았지만 읽기 전용 연결은 커밋된

저널 때문에 열리지 않을 수 있다. 그 경우 게이트는 "확인 불가"로 막히고, 쓰기 연결이 한 번
열리면 복구된다 — 테스트는 두 경우를 모두 받아들인다.

다시 돌리지 않고 인용하는 기존 증거(`tests/test_real_validation_risk.py`,
`test_real_validation_gate.py`): 같은 프로세스 안의 두 연결 경쟁, 저장소 재오픈 뒤 예약·중단
유지, 추가 전용 트리거, 재개 결정 중복 거부, 다른 스키마 버전 차단.

검증하지 않은 것: 전원 차단(OS 캐시 유실), 네트워크 드라이브, 디스크 가득 참, 실제 매수
경로와의 연동(연결 자체가 없다).

## 7. 증거 감사 (합성)

**실제 PASS 증거는 한 건도 없다.** 아래는 합성 저장소로 감사 절차가 동작하는지 본 것이다.

`scripts/real_validation_audit.py`는 검증 디렉터리 하나를 읽기 전용으로 감사한다: SQLite
무결성, 증거 해시 사슬, 등록과의 결합, 입력 원본 해시, 판정 코드 해시, 실행 환경, 그리고
**수익성 판정을 저장된 입력으로 다시 계산**한 결과.

합성 저장소에 돌린 결과(`evidence_audit_synthetic.json`): 무결성 ok, 사슬 문제 0건(기원
해시 → 수익성 행 → 경로 행, 머리 `a2992806…`), 수익성 증거 재계산 PASS = 기록 PASS, 결합
PASS, 판정 코드·실행 환경 일치. 게이트는 닫혀 있다 —
`PRE_BUY_ENFORCEMENT_WIRED=False`를 우회하지 않았고 감사가 자격을 주지도 않는다.

이번에 채운 공백(`tests/test_real_validation_audit.py`, 18개 통과):

| 상황 | 결과 |
|---|---|
| 비용 정책 **내용** 변경 | `STALE_COST_POLICY_HASH`로 차단 (전에는 파일 삭제만 확인) |
| 체결 모델 내용 변경 | `STALE_FILL_MODEL_HASH`로 차단 |
| 경로 판정 코드만 변경 | 경로 증거만 낡고 수익성 증거는 유지 |

| 저장소가 절반으로 잘림 / 페이지가 덮어쓰임 | 게이트 차단, 감사 실패, 청산은 허용. 손상 파일을 고쳐 쓰지 않음 |
| 등록 행 삭제 | 증거가 결합할 곳을 잃어 차단 |
| 기록은 PASS인데 저장된 입력은 손실 표본 | 사슬은 멀쩡하고 재계산 감사가 잡음 |
| 중단·미결 예약이 있는 저장소 | 감사가 나열. 매도·취소·대사 허용 |
| 실행 환경이 판정 때와 다름 | 표시만 하고, 재계산이 같으면 문제로 올리지 않음 |

감사 범위:

- 판정 코드 해시가 덮는 파일은 수익성 `core.py`·`costs.py`·`profitability.py`, 경로
  `core.py`·`execution_profile.py`다.
- 그 파일들이 임포트하지만 해시 밖인 저장소 모듈: `evidence.py`·`store.py`(배선),
  `src/modules/cost_model.py`(연구 비용 상수 — 바뀌면 비용 정책 해시가 대신 어긋난다).
  새 임포트가 생기면 테스트가 분류를 요구한다.
- 서드파티 의존성은 판정 경로에 없다(표준 라이브러리만 쓴다).
- **덮지 못하는 것:** 파이썬 인터프리터·표준 라이브러리·OS 바이너리. 증거에 실행 환경
  (파이썬·SQLite 버전, 플랫폼)을 기록하게 했고, 달라졌을 때는 재계산으로 결과가 같은지
  본다. 바이너리 자체를 검증하지는 않는다.
- 저장된 입력이 실제 거래 DB와 같은지, 저장소가 통째로 바뀌었는지는 이 감사로 알 수 없다.
  판정 때 사슬 머리 해시를 git에 남기는 절차가 여전히 필요하다.

## 8. 남은 검증과 결정

미완료 운영 검증:

- REAL 서버 읽기 전용 타이밍 — 3절의 PAPER 값과 짝이 될 REAL 표본이 없다
- 실제 판단부를 건 PAPER·REAL 재생
- 잠금 미래 표본 수집과 수익성 판정
- 증권사 정산 대사, 실계좌 수수료율 확인, 코스피 농특세 본문 확인
- 호가 잔량(여러 단계) 수집과 그에 기반한 유동성 한도 평가
- 매수 경로 연결(전략 파일 변경) — 그때까지 REAL은 어떤 설정으로도 차단
- 전원 차단·디스크 장애 수준의 저장소 장애

이번 결과가 결정에 주는 것:

1. **호가 신선도 논의의 대상을 바꿔야 한다.** 한도(1,500/500ms)는 승인 시점 검사이고
   그때는 늘 0ms다. 실제로 호가를 늙게 하는 것은 주문 호출의 간격 대기다. 경로 계약에는
   "전송 시점의 호가 나이"를 모드별로 재서 넣는 것이 맞다.
2. **위험 초안에서 일일 중단선과 낙폭 한도는 이 전략의 과거 손실 크기로는 닿지 않는다.**
   안전판으로 두는 것은 타당하지만, 일상적으로 걸리는 것은 연속손실 중단이고 한 달에
   한두 번 검토가 필요하다. 검토 기간과 재개 기준을 정해야 한다.
3. **스트레스 손실률은 3% 미만으로 잡을 근거가 없다.** 손실 거래의 95%가 2.93% 안이고
   최대가 5.6%다. 다만 이것은 PAPER 체결이고 주문 크기가 달랐다.
4. **수수료율이 평균 손익의 부호를 정한다.** 증권사 약정 확인이 비용 정책의 첫 항목이다.
5. **부분 체결은 PAPER에서도 일어난다**(진입 4건). 주문 예산 장부의 부분 체결 처리가
   필요한 기능이었다.
