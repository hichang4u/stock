# 테이블 설계 요약

> 상세 컬럼과 SQL 정의의 원천은 `docs/DB_DESIGN.md`입니다.  
> 이 문서는 테이블의 책임, 관계, 화면별 데이터 원천만 빠르게 확인하기 위한 지도입니다.
> 최종 수정: 2026-08-06

## 테이블 책임

| 테이블 | 책임 | 주 사용처 |
|---|---|---|
| `trades` | 하루 거래 1건의 진입부터 청산까지의 생명주기 | 이력, 통계 |
| `orders` | KIS 주문 의도, 제출 상태, 체결, 취소, 실패 결과 | 주문·응답 유실 복구 |
| `partial_exits` | F4 1차 익절 상세 | 이력, 통계 |
| `daily_skips` | 당일 거래 스킵 또는 진입 중단 사유 | 이력, 진단 |
| `asset_snapshots` | KIS 잔고 조회 성공 결과의 감사/장애 분석 이력 | 자산 |

## 관계

```text
trades 1 ── N orders
trades 1 ── N partial_exits
orders 1 ── N partial_exits

daily_skips      # date 기준 업무 연결, FK 없음
asset_snapshots  # 조회 시각 기준 누적 이력, FK 없음
```

`daily_skips`는 `trades.date`와 같은 거래일 개념을 공유하지만 거래가 생성되지 않은 날도 기록해야 하므로 FK를 두지 않습니다.

`asset_snapshots`는 특정 거래의 하위 데이터가 아니라 KIS 잔고 조회 시점별 계좌 상태입니다. 주문 판단 근거를 사후 확인하기 위한 이력이라 거래 테이블과 직접 연결하지 않습니다.

## 화면별 원천

| 화면 | 주 원천 | 보조 원천 |
|---|---|---|
| 오늘 | `/api/status`, JSONL 로그, 원시 tick/분 단위 메모리 버퍼 | `trade_marks`, `asset_snapshots` fallback |
| 자산 | KIS 잔고 조회 `/api/assets` | 마지막 `asset_snapshots` |
| 주문 | `orders` + `trades` JOIN | JSONL 로그 이벤트 |
| 이력 | `trades` | `orders`, `partial_exits` |
| 통계 | `trades` | `partial_exits` |

## 저장 정책

| 데이터 | 저장 방식 |
|---|---|
| 주문/체결 | 주문 전 로컬 상관 ID와 의도를 `orders`에 먼저 저장하고 제출·체결 상태를 갱신 |
| 거래 생명주기 | 진입 시 `trades` 생성, 청산 시 갱신 |
| 1차 익절 | 발생 시 `partial_exits` 저장 |
| 거래 스킵 | 당일 1행을 `daily_skips` 저장 |
| 자산 조회 | KIS 조회 성공 시마다 `asset_snapshots` 저장 |
| 진행 단계/진단 이벤트 | DB가 아니라 JSONL 로그 기준 |
| 원시 tick | 메모리 deque 최대 5,000개, 프로세스 재시작 또는 거래일 변경 시 초기화 |
| 분 단위 가격 | 메모리 deque 최대 180분, 같은 분의 마지막 가격과 tick 수 유지 |

## 오늘 가격흐름 조합

- `tick_history`: 진입 이후의 최근 원시 tick(최대 5,000건). 최근 구간의 세밀한 선과 SSE 증분 갱신에 사용합니다.
- `minute_price_history`: 원시 tick 버퍼가 담지 못한 앞 구간을 분 단위 마지막 가격으로 보완합니다(최대 180분).
- `minute_price_seed`: 분 이력 180분에서도 밀려난 앞 구간을 **저장된 1분 봉의 종가**로 보완합니다(읽기 전용).
  출처는 수집 중이면 `bars.series`(메모리), 아니면 `data/bars/<날짜>_<종목>.json`입니다.
  `minute_price_seed_meta.source`가 출처(`memory`/`file`)와 사정(`none` 파일 없음, `error` 읽기 실패,
  `skipped` 보완할 구간 없음)을 알려 줍니다.
- `trade_marks`: 당일 `orders`의 체결 데이터를 종목별·체결시각 오름차순으로 조회해 매수/매도 마커와 가격 fallback에 사용합니다.
- 위 데이터는 운영 화면용 조회 모델이며 SQLite에 새로운 시세 테이블을 만들지 않습니다.

### 세 자료를 한 선으로 합치는 기준

우선순위는 **WS tick > 메모리 분 > 저장 분봉**입니다(`composePriceFlowPoints`, `price_seed_from_bars`).

| 항목 | 기준 |
|---|---|
| 분 키 | 셋 다 "분의 시작 시각". 다만 봉은 거래소 체결시각, 메모리 분은 수신 시각으로 나눈 것이라 분 경계의 체결이 서로 다른 분에 들어갈 수 있습니다 |
| 겹치는 분 | 섞지 않습니다. 저장 분봉은 메모리 분 이력의 **첫 분보다 앞선 분만** 씁니다 |
| 찍는 시각 | 분 단위 값은 그 분의 마지막 체결가이므로 **분이 끝난 시각**(시작+60초, 진행 중인 분은 지금)에 찍습니다. 분 시작에 찍으면 최대 59초 뒤 가격이 앞당겨 보입니다 |
| tick과의 경계 | 첫 tick 시각부터는 tick만 씁니다 |
| 창 | 보유·청산은 진입 분부터, 미보유 관측은 그날 0시(KST)부터. 진입 시각을 모르면 저장 분봉을 쓰지 않습니다 |
| 끝나지 않은 분 | 저장 분봉에서는 뺍니다(종가가 아직 바뀝니다) |
| 못 쓰는 값 | 종가가 유한한 양수가 아니거나 시각·날짜가 맞지 않는 봉은 버리고 `invalid`로 셉니다 |
| 빈 분 | 앞뒤 값으로 채우지 않습니다. 관측이 5분 넘게 비면 선을 잇지 않고, 화면의 "선:" 줄에 적습니다 |
| 중복·역순 | 같은 분은 뒤 행이 이깁니다. 시각이 뒤로 가는 tick과 바로 앞과 같은 tick은 버립니다 |

보관 범위는 그대로입니다 — 메모리 tick 5,000건, 메모리 분 180분(`src/live.py`). 하루 전체가 보이는 것은
한도를 늘려서가 아니라 저장 분봉을 읽어서입니다. 저장 분봉이 없거나 읽지 못한 구간은 비워 두고 이유를 표시합니다.

## 유지보수 규칙

- 컬럼 추가/제약 변경은 `src/db.py`와 `docs/DB_DESIGN.md`를 먼저 갱신합니다.
- 이 문서에는 컬럼 표를 중복 작성하지 않습니다.
- `asset_snapshots.raw_json`에는 계좌 상태 값이 포함될 수 있으므로 외부 공유 대상에서 제외합니다.
