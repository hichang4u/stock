# 트랙 B 재생 하네스 설계

**목표** — 규칙 하나를 시험하는 비용을 몇 분으로 줄여, 트랙 A를 이길 만한 도전자를
찾을 확률을 올린다.

**배경** — 챔피언(A) / 도전자(B) 순환 운용이 최종 목표다. 그런데 현재 도전자 후보
R1·R2·R3은 백테스트에서 전부 진다(각각 −12.5% / −6.2% / −16.4%). 실시간 B 엔진을 먼저
지으면 그 인프라를 "지는 걸 아는 규칙"을 몇 달간 관찰하는 데 쓰게 된다. 규칙 탐색이
먼저다.

**선행 스펙**
- `docs/superpowers/specs/2026-08-25-multi-track-strategy-design.md` (모스펙)
- `docs/superpowers/specs/2026-08-27-track-b-shadow-design.md` (그림자)
- `docs/superpowers/specs/2026-08-28-track-b-rule-selection-design.md` (선정)

## 1. 완료 정의

다음이 되면 끝이다.

1. 새 규칙 함수를 `scripts/track_b_rules.py`에 하나 추가하고 한 명령을 돌리면,
   52거래일 표본에 대한 관문 판정과 손익 분포가 나온다.
2. 그 실행이 KIS를 호출하지 않는다 — 분봉이 이미 캐시에 있다.
3. 캐시가 비어 있으면 한 명령으로 채운다 — 워밍업 없이 약 11분, 전 거래일까지 받으면
   약 22분(2.2절).

실시간 B 엔진, 실전 승격, 챔피언 교체 절차는 **이 스펙의 범위가 아니다.**

## 2. 확정된 사실

설계는 추정이 아니라 아래 실측 위에 선다.

### 2.1 KIS 과거 분봉은 약 1년치가 온다 (2026-09-11 실측)

`inquire-time-dailychartprice` / `FHKST03010230`, 종목 005930 기준.

| 대상일 | 며칠 전 | 결과 |
|---|---|---|
| 2026-09-09 ~ 2026-06-24 | 1 ~ 78 | 정상 (120봉/호출) |
| 2026-04-01 | 162 | 정상 |
| 2026-01-02 | 251 | 정상 |
| 2025-10-02 | **343** | 정상 |
| 2025-07-02 | 435 | **0봉 — 한계** |

코드 주석의 *"과거 관측일 소급용이며 가용성은 미검증이다"*
([kis_minute_bars.py:133](../../../src/api/kis_minute_bars.py#L133))는 이로써 검증됐다.
주석을 갱신한다.

한 종목 하루는 **4호출**로 전 세션이 덮인다 (2026-08-21 실측).

```
page1  120봉  13:21~15:30
page2  120봉  11:22~
page3  120봉  09:23~
page4   24봉  09:00~
       381봉  09:00:00~15:30:00
```

트랙 B가 쓰는 09:35~14:00 구간이 완전히 들어온다.

### 2.2 유니버스는 복구 불가, 로그에서 부분 복원만 된다

`data/f1_snapshots`는 09:00 실시간 예상체결 상태라 그 시각에만 존재한다. 2026-09-03에
`git worktree remove`가 정션을 따라가 `f1_snapshots`와 `backtest_bars`를 통째로 지웠고,
직후 백업(`data_20260903_122113`)에도 `f1_snapshots`가 0일이다. 8월 28일 백테스트가
쓴 22거래일은 **영구 소실**이다.

현재 남은 원본은 4일치(09-04, 09-08, 09-09, 09-10)다.

로그에서 건질 수 있는 것 (2026-09-11 전수 집계):

| 출처 | 일수 | 담긴 것 |
|---|---|---|
| `TARGET_LOCKED` | **52일** (2026-07-01 ~ 09-10) | 순위대로 최대 3종목 |
| `f1_snapshots` 원본 | 4일 | 60종목 전 속성 |

`TARGET_LOCKED`는 하루에 여러 번 난다(총 154건). `target_tickers` 필드는 도중에
추가되어 2026-06-29에는 없다.

총 **149개 (날짜, 종목) 쌍** → 분봉 596호출 → PAPER 초당 1건에서 **약 11분**.

이는 워밍업 없이(`--warmup-days 0`) 계산한 값이다. R1은 "그날 09:00부터의 고가"만 보므로
전 거래일 봉이 필요 없다. 반면 SMA·MACD를 쓰는 규칙은 전 거래일이 필요하고,
`needed_pairs(warmup_days=N)`가 각 종목의 앞 N거래일을 대상에 더한다
([track_b_backfill.py:156](../../../scripts/track_b_backfill.py#L156)). `warmup_days=1`이면
쌍이 약 두 배(≈298)가 되어 **1,192호출 ≈ 22분**이다. 캐시는 누적되므로 이 비용은
규칙군마다 한 번만 든다.

### 2.3 복원되는 것은 "랭킹"이 아니라 "이미 매겨진 순위"다

`TARGET_LOCKED`는 종목 코드와 순서만 남기고, 종목별 갭·대금·거래량은 1위 것만 남긴다.
따라서 `f1_selector.rank_candidates()`를 다시 돌릴 수 없다. F1 선정 규칙 자체를 바꿔
보는 실험은 이 표본으로 할 수 없고, **F1 결과를 입력으로 받는 트랙 B 진입 규칙 실험만**
할 수 있다.

이는 제약이지 결함이 아니다 — 선정 설계 §4.1이 "B가 A와 다른 점을 진입 시각 하나로
줄인다"고 고정했으므로, F1은 어차피 통제 변수다.

## 3. 이 하네스가 답할 수 있는 질문과 없는 질문

이 절이 하네스의 존재 이유를 규정한다. 여기를 오해하면 나온 숫자를 잘못 쓴다.

트랙 A 실측: 39건, 평균 **+0.137%**/거래, 표준편차 **2.936%**,
95% 신뢰구간 **−0.78% ~ +1.06%** — **0을 포함한다.** 승률 41.0%.

표준편차 2.936%에서 두 전략의 차이를 80% 검정력으로 검정하려면:

| 잡으려는 차이 | 필요 표본/트랙 |
|---|---|
| 0.3%p | 1,533건 |
| 0.5%p | 552건 |
| 1.0%p | 138건 |

하루 0.8건 빈도에서 52일 표본은 최대 수십 건이다.

**답할 수 없는 질문** — "이 규칙이 A보다 낫다." 표본이 두 자릿수인 한 어떤 우열도
노이즈와 구분되지 않는다. 규칙을 여러 개 스윕하면 다중비교로 "가장 운 좋았던 것"이
1등으로 올라온다.

**답할 수 있는 질문**
- **신호가 나는가.** 22거래일에 진입일 3일 미만이면 판정 불가다 (선정 설계 §5.1).
- **명백히 지는가.** R1의 −12.5%처럼 큰 음수는 적은 표본으로도 보인다.
- **부호가 안정한가.** 체결 가정 0.0 / 0.2 / 0.4%를 얹어 부호가 뒤집히면 탈락
  (선정 설계 §5.2).
- **구조적으로 설명되는가.** 사람이 판단한다 (선정 설계 §5.4).

즉 이 하네스는 **선별기가 아니라 거름망**이다. 통과는 "실전 관찰 대상으로 승격"을
뜻하지 "채택"을 뜻하지 않는다.

## 4. 구성요소

세 조각이고, 각각 따로 돌릴 수 있다.

```
로그 62일치 ──▶ [1] 유니버스 복원기 ──▶ data/replay/universes.json
                                              │
                                              ▼
KIS 과거 분봉 ─▶ [2] 분봉 수급기 ──────▶ data/backtest_bars/{date}_{ticker}.json
                                              │
                                              ▼
                          [3] 규칙 스윕 ──▶ data/replay/sweep_{ts}.json + 화면 표
```

### 4.1 유니버스 복원기 (신규)

`scripts/replay_universe.py`

로그 디렉터리를 훑어 `TARGET_LOCKED`에서 (날짜, 순위, 종목)을 뽑는다.

- 하루에 여러 이벤트가 있으면 **`target_tickers`가 비어 있지 않은 마지막 것**을 쓴다.
  F2가 재시도로 종목을 바꾼 경우 실제로 진입 시도한 조합이 마지막이기 때문이다.
- `target_tickers`가 없거나 빈 날은 건너뛴다 (2026-06-29 한 건).
- 로그 디렉터리는 인자로 받는다. 운영 트리의 `data/logs`와 개발 트리의
  `data/logs.migrated`를 둘 다 읽어야 62일이 모인다.

출력은 순위가 보존된 목록이다.

```json
{
  "generated_at": "2026-09-11T00:00:00+09:00",
  "source_dirs": ["D:/Private/stock/data/logs.migrated", "..."],
  "days": {
    "20260910": [
      {"rank": 1, "ticker": "187660"},
      {"rank": 2, "ticker": "484810"},
      {"rank": 3, "ticker": "024060"}
    ]
  }
}
```

이 파일은 **로그에서 언제든 재생성된다.** 소실돼도 손실이 아니다 — 2.2절의 사고가
남긴 교훈은 "재생 불가 자산만이 진짜 자산"이다.

### 4.2 분봉 수급기 (기존 확장)

`scripts/track_b_backfill.py`

현재는 `strategy_backtest.load_universes()`로 `f1_snapshots`를 읽는다. 여기에
**`--universes <path>` 인자**를 더해 4.1의 출력도 받게 한다. 기존 경로는 그대로 둔다.

페이징·캐시·완결성 판정(`is_session_complete`)은 이미 있고 실측으로 동작이 확인됐다.
새로 필요한 것은 입력 경로 하나뿐이다.

### 4.3 규칙 스윕 (기존 확장)

`scripts/track_b_backtest.py`

`simulate_day()`는 지금 `f1_selector.rank_candidates(universe)[:depth]`로 순위를
매긴다([track_b_backtest.py:97](../../../scripts/track_b_backtest.py#L97)). 복원된
유니버스에는 순위를 다시 매길 속성이 없으므로(2.3절), **이미 매겨진 순위를 그대로 받는
경로**를 연다.

```python
def simulate_day(
    date: str,
    universe: list[dict],
    ...,
    ranked_tickers: list[str] | None = None,   # 추가
) -> dict | None:
    if ranked_tickers is None:
        ranked = f1_selector.rank_candidates(universe)[:depth]
        ranked_tickers = [str(r["ticker"]) for r in ranked if r.get("ticker")]
    else:
        ranked_tickers = ranked_tickers[:depth]
```

`universe`가 빈 리스트여도 `ranked_tickers`가 있으면 돈다. 이후 로직은 종목 목록과
분봉만 쓰므로 손댈 곳이 없다.

**새 규칙을 꽂는 자리**는 `track_b_rules.py`의 순수 함수 하나다. 규칙 키를 스윕
대상 목록에 넣으면 그대로 표에 한 줄이 는다.

## 5. 안전

### 5.1 장중에 돌리지 않는다

두 트리의 프로세스는 **각자 독립된 레이트 리미터**를 가진다
(`kis_rest._rate_waiters`는 모듈 전역이고 프로세스마다 따로 산다). 계좌 유량 한도는
공유되는데 리미터는 공유되지 않으므로, 개발에서 596호출을 쏘면 운영의 초당 1건 예산을
그대로 잠식한다. 개발이 BACKGROUND 우선순위를 써도 이건 **프로세스 내부 우선순위**라
운영에는 보이지 않는다.

- 수급기는 **장 종료 후(15:30 이후) 또는 개장 전(09:00 이전)에만** 돌린다.
- `in_forbidden_window()`(09:00~09:11)는 이미 코드에 있고 그대로 둔다. 그것만으로는
  부족하다는 것이 위 문단의 요지다.
- 실행 시 시각을 확인하고 장중이면 거부한다. `--force`로 넘길 수 있게 하되 경고를
  찍는다.

### 5.2 주문 경로를 타지 않는다

시세 GET만 쓴다. 수급기는 `CallBudget`으로 상한을 걸고, 기본값은 (날짜×종목×4)+여유로
계산해 넘으면 중단한다.

### 5.3 운영 데이터를 쓰지 않는다

복원기는 로그를 **읽기만** 한다. 출력은 개발 트리의 `data/replay/`에만 쓴다. 운영
트리의 `data/`에는 어떤 경로로도 쓰지 않는다.

## 6. 테스트

| 대상 | 검증 |
|---|---|
| 복원기 | 합성 로그 3일치(이벤트 여러 개, 빈 목록, 필드 없음)에서 마지막 비어있지 않은 것을 고르는지 |
| 복원기 | 두 디렉터리를 합칠 때 같은 날짜가 중복되면 나중 것을 쓰는지 |
| 수급기 | `--universes` 입력이 기존 `f1_snapshots` 경로와 같은 구조를 내는지 |
| 수급기 | 장중 시각이면 거부하고 `--force`로 넘어가는지 |
| 스윕 | `ranked_tickers`를 주면 `rank_candidates`를 부르지 않는지 |
| 스윕 | `ranked_tickers`가 `depth`보다 길면 잘리는지 |

KIS를 때리는 테스트는 쓰지 않는다. 수급기는 응답을 목으로 넣어 페이징만 본다.

## 7. 이 스펙이 만들지 않는 것

- **실시간 B 엔진.** 도전자가 나온 뒤의 일이다.
- **실전 승격 절차.** 오늘 만든 트리 분리로 대부분 준비돼 있고, 승격 판단 기준은
  도전자가 생긴 시점에 정한다.
- **F1 선정 규칙 실험.** 2.3절의 제약으로 이 표본에서는 불가능하다.
- **f1_snapshots 보관 강화.** `F1_SNAPSHOT_KEEP=400`은 이미 넉넉하고, 2026-09-03
  사고의 원인은 보관 정책이 아니라 `git worktree remove`였다. 트리를 분리하며
  worktree를 쓰지 않게 된 것이 재발을 막는다.

## 8. 열린 질문

**표본이 52일에서 늘어나는 속도.** 지금부터는 `f1_snapshots` 원본이 온전히 쌓이므로
하루에 하루씩 는다. 60종목 전 속성이 남으므로 F1 랭킹 재계산도 가능해진다. 즉 시간이
지날수록 이 하네스의 입력이 좋아진다. 언제 52일 표본을 버리고 원본 기반으로 갈아탈지는
그때 판단한다.
