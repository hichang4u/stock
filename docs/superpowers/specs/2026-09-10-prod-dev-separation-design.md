# 운영·개발 환경 분리 설계

작성일: 2026-09-10
범위: 하위 프로젝트 A (배포 경로 분리). 하위 프로젝트 B(과거 날짜 재생 하네스)는 별도 스펙.

## 배경

운영 프로세스가 개발 중인 작업 트리(`D:\Private\stock`)에서 그대로 돈다. 워치독
Task Scheduler도 같은 경로를 가리킨다. 그래서 **파일을 고치는 것이 곧 배포다.**
승격 절차도, 검사도, 기록도 없다.

2026-09-10에 이 구조가 실제로 발현됐다. `.env`의 `PAPER_FAST_HYBRID`를 `0`에서
`1`로 바꾸자 아무 게이트도 거치지 않고 다음 거래일 08:00 기동에 반영되는 상태가
됐다. 변경 자체는 사전 등록된 기준을 통과한 유효한 결정이었지만, 그 사실과
무관하게 **배포 경로에는 아무 마찰도 없었다.**

### 증거가 쌓이지 않는다

`readiness.py`의 `stable_paper_trades` 게이트는 "현재 코드 지문으로 PAPER 정상청산
20회"를 요구한다. DB의 트랙 A PAPER 정상청산을 지문별로 세면 이렇다.

```
지문 11개, 최대 3건, 목표 20건
cdd527e899da 3 / 39cf806f8eac 3 / c23756fde5c2 2 / 3401f8c50155 2 /
20e1be68b17c 2 / 나머지 6개 각 1건
```

전략을 바꿀 때마다 지문이 갈리고 카운터가 0부터 다시 시작한다. 배포에 마찰이
없으니 지문이 계속 갈렸고, 그래서 REAL 전환 게이트는 한 번도 근처에 간 적이 없다.
2026-09-10 변경도 `cdd527e899da`(3건) → `833edca5fff4`(0건)로 한 줄을 더한다.

## 요구사항

1. 운영은 지금 도는 것. 편집이 곧 배포가 되면 안 된다 — 명시적 승격만.
2. 개발 트리는 아무 때나 즉시 실행 가능해야 한다.
3. 개발은 `KIS_MODE=PAPER` 고정. REAL은 구조적으로 불가능해야 한다.
4. 개발도 주문을 포함한 전 권한을 갖는다.
5. 계좌는 공유하되 예산을 나눈다.
6. 종목이 충돌하면 개발이 다음 순위로 회피한다.
7. 개발이 운영 `data/`를 오염시키지 않는다. 재생용 읽기는 허용한다.

## 1. 디렉터리 구조와 역할

```
D:\Private\stock          개발  — main 브랜치, 자유롭게 편집
D:\Private\stock-prod     운영  — detached HEAD @ 릴리스 태그
```

각 트리가 독립적으로 갖는 것: `.venv`, `.env`, `data/`, `main.pid`, UI 포트.

운영은 **별도 clone**으로 둔다. worktree는 `.git`을 개발 트리와 공유해서, 개발 쪽
`.git`이 손상되면 운영도 같이 죽는다. 운영은 혼자 살아남아야 한다.

### 자동으로 격리되는 것

- `main.pid` — `PID_PATH`가 `main.py` 파일 위치 기준이다 (`main.py:59`)
- `data/*` — 경로 설정이 전부 CWD 상대경로다 (`LOG_DIR=data/logs` 등)

### 역할 표식

각 트리 루트에 `.stock-role` 파일 하나. 내용은 `prod` 또는 `dev`. 런처·승격
스크립트·계좌 단위 스크립트가 전부 이 파일을 읽는다. **파일이 없으면 기동을
거부한다** — 역할 불명인 트리가 도는 상황을 만들지 않는다.

## 2. 승격 경로

태그 규칙은 `release/YYYYMMDD-N`. 현재 태그 0개에서 시작한다.

```powershell
# 개발 트리
git commit ...
scripts\preflight.ps1          # ruff + mypy + pytest + 지문 변경 여부 출력
git tag release/20260911-1
git push origin main --tags

# 운영 트리
scripts\promote.ps1 -Tag release/20260911-1
```

`promote.ps1`이 하는 일:

1. `.stock-role`이 `prod`인지 확인 (개발에서 실행되면 즉시 중단)
2. `git fetch origin --tags`
3. 태그 존재 확인, 현재 HEAD와의 차이 표시
4. `restart_guard.py`로 안전 상태 확인 — 포지션이 `IDLE`/`CLOSED`가 아니면 거부
5. `git checkout <tag>` (detached)
6. `restart_main.ps1` 경유 재시작

`origin`을 거치는 이유는 운영이 지금 어느 커밋인지 GitHub에 남기기 위해서다.
개발 트리를 날려도 운영을 재현할 수 있다. 오프라인일 때만 운영이 개발 트리를
로컬 remote로 fetch하는 우회로를 둔다.

새로 만드는 것은 `preflight.ps1`과 `promote.ps1` 둘뿐이다. 나머지는 기존
`restart_guard.py`·`restart_main.ps1`·`start_main.ps1`을 그대로 쓴다.

## 3. 승격 기준 — 지문 기반 2단 게이트

`strategy_fingerprint()`(`src/release.py`)는 전략 파일 20개와 전략 env override의
12자리 해시다. "이 배포가 매매 동작을 바꾸는가"에 기계적으로 답한다.

### 공통 (모든 승격, 자동, 하나라도 실패하면 중단)

1. `ruff check .` — 0건
2. `mypy` — 통과
3. `pytest` — 전체 통과 (2026-09-10 기준 1331건)
4. 태그가 그 커밋을 정확히 가리키고 워킹트리 클린
5. `restart_guard.py` — 운영이 `IDLE`/`CLOSED`

### 1단 · 지문 무변경

문서, 테스트, 스크립트, 관측 전용 모듈(`tick_capture`, `f1_snapshot_selector` 등).
공통만 통과하면 승격한다. 매매 동작이 안 바뀌니 증거 카운터도 안 깨진다. 부담
없이 자주 올리는 경로다.

### 2단 · 지문 변경

전략 파일 20개, 또는 `F1_`~`F5_`/`PAPER_FAST_`/`VI_`/`TRAILING_SHADOW_` 등
override. 공통에 더해 아래를 표시하고 확인받는다.

- 새 지문과 **리셋되는 것**: `stable_paper_trades` N건 → 0,
  `baseline-<지문>` 실험 재시작
- 변경 근거 문서 링크. 사전 등록된 기준이 있으면 그 판정 결과
- 재생 검증 결과 — **B 구현 후 필수**. 그 전까지는 "미구현" 사유를 기록에 남긴다

**목적은 자동 차단이 아니라 비용을 보이게 만드는 것이다.** 승격을 막는 게
목적이면 개발이 느려질 뿐이다. 2026-09-10 전환도 기준을 통과했고 옳은 결정이었지만
"증거 3건이 0이 된다"는 사실은 아무도 몰랐다.

### 비대화형 실행

승격은 Claude가 요청받아 실행할 수 있어야 한다. 에이전트 도구는 stdin이 닫힌 채로
돌기 때문에 확인을 `Read-Host` 프롬프트로만 구현하면 실행이 불가능하다. 플래그로도
받되, 맹목적으로 붙일 수 없게 **예상 지문을 명시**하도록 묶는다.

```powershell
# 1단 — 플래그 불필요
scripts\promote.ps1 -Tag release/20260911-1

# 2단 — 승격 후 실제 지문과 일치해야만 진행. 다르면 중단
scripts\promote.ps1 -Tag release/20260911-1 -AcknowledgeFingerprint 833edca5fff4
```

값을 알려면 `preflight.ps1`을 먼저 돌려야 하므로, 이 플래그는 "이미 지문을
확인했다"는 증거가 된다.

"운영 배포해줘" 요청에 대한 동작:

| 상황 | 동작 |
|---|---|
| 1단 | 공통 검사 후 바로 승격, 결과 보고 |
| 2단 | 지문 diff와 리셋되는 증거 건수를 먼저 보여준 뒤 승격 |
| 검사 실패 | 승격하지 않고 실패 출력 그대로 보고 |
| 운영이 포지션 보유 중 | `restart_guard`가 차단. 청산 후로 미룸 |

막으려는 것은 **아무도 결정하지 않은 배포**이지 배포 자체가 아니다.
"운영 배포해줘"는 결정이므로 바로 실행한다.

## 4. 기동 거부 조건

`start_main.ps1`의 기존 7단계 사전점검에 역할별 8단계를 추가한다.

| 역할 | 추가 검사 |
|---|---|
| `prod` | HEAD가 릴리스 태그에 정확히 위치 / 워킹트리 클린 |
| `dev` | `KIS_MODE`가 `PAPER`가 아니면 거부 / 데이터 경로가 운영 경로면 거부 |

운영 트리에서 파일을 고치면 워킹트리가 더티해져 다음 기동이 거부된다. 태그를
벗어나도 거부된다. 이것이 "편집이 곧 배포"를 끊는 지점이다.

## 5. 개발 런타임 격리

| 항목 | 개발 설정 | 근거 |
|---|---|---|
| `main.pid` | 자동 분리 | 파일 위치 기준 |
| `data/*` | 자동 분리 | CWD 상대경로 |
| `UI_PORT` | `8898` (운영 8899) | 포트 충돌 방지 |
| `KIS_MODE` | `PAPER` 고정, 아니면 기동 거부 | 런처 역할 검사 |
| 워치독 | 없음 (수동 기동만) | 밤새 혼자 살아나지 않게 |

읽기 전용으로 운영을 참조하는 경로는 둘뿐이다.

- `AUTH_DIR` → 운영의 `data/auth` 공유. 개발은 캐시를 읽기만 하고 **발급하지
  않는다** (`KIS_AUTH_READONLY=1`). 만료되면 조용히 실패하는 대신 "운영 토큰
  만료"를 크게 알린다. 운영이 유일한 발급자다.
  플래그를 생략하면 `.stock-role`이 기본값을 정한다 — 개발이면 읽기 전용.
  `.env`에서 빠뜨려도 안전한 쪽으로 기울게 하려는 것이고, 명시된 값은 항상
  역할을 이긴다(6-5절의 REAL 전환이 이 override를 쓴다). 읽기 전용은 발급
  (`refresh`), 캐시 쓰기(`_save_cache`), 폐기(`revoke`) 세 가지를 모두 막는다 —
  폐기는 운영이 쓰는 바로 그 토큰을 KIS에서 죽이기 때문이다.
  **이 공유는 운영도 PAPER일 때만 성립한다** — REAL 토큰은 발급 호스트가 달라
  개발이 쓸 수 없다. 6-5절 참조.
- `REPLAY_SOURCE_DIR` → 운영의 `data/` (프로브·스냅샷·틱). B가 쓸 재생 원본.

토큰 공유의 안전성은 실측으로 확인한다. 같은 앱키로 두 트리가 각자 발급하면 운영
토큰이 무효화될 수 있다. 읽기 전용 기본값은 fail-safe다 — 틀렸을 때의 실패 방향이
"개발이 못 돎"이라 운영에 해가 없다.

## 6. 계좌 공유 규칙

**이 절의 규칙은 운영이 PAPER일 때만 적용된다.** 운영이 REAL로 전환되면 계좌가
물리적으로 분리되므로 예산 분할과 종목 충돌 회피는 의미를 잃는다. 모드별 적용
범위는 6-5절에 정리한다.

### 예산 — 코드 변경 없이 기존 노브로 (운영 PAPER 한정)

`F3_ALLOC_RATIO`(현재 0.95)를 운영 `0.70` / 개발 `0.30`으로 나눈다. 운영이
09:00에 먼저 70%를 쓰고, 개발은 09:11 이후 남은 30%를 쓴다. 순서가 고정돼 있어
절대금액 상한을 새로 만들 필요가 없다.

비율을 살아있는 `ord_psbl_cash`에 곱하는 것은 원래 함정이다 — 개발이 쓴 만큼 운영
몫도 같이 줄어든다. 여기서는 **운영이 항상 먼저 실행되므로** 그 함정에 걸리지
않는다. 이 순서가 무너지면 예산 분리도 무너진다.

### 종목 충돌 — 개발이 다음 순위로

F5는 상태 파일이 아니라 브로커의 계좌 전체 `hldg_qty`로 매도 수량을 정한다
(`f5_timeout.py:118`, `f5_timeout.py:62-64`). 개발과 운영이 같은 종목을 들면
**운영 F5가 개발분까지 전량 매도한다.**

개발 F3가 진입 직전 계좌 보유종목(`inquire-balance` `output1`)을 조회해 이미
보유 중인 종목을 후보에서 제외하고 다음 순위로 내려간다. 기존 `candidate_rank`
1→2→3 회전 구조를 그대로 쓴다. `DEV_EXCLUDE_HELD_TICKERS=1`로 개발에서만 켠다.

### 시간 — 개발은 09:11 이후

운영의 F3 체결 마감(`F3_FILL_DEADLINE`) 이후에만 개발이 진입한다. 개장 창에서
레이트 제한을 다투지 않고, 그 시점엔 운영 종목이 확정돼 있어 제외 목록이 정확하다.
`schedule_times.py`가 현재 상수이므로 env 오버라이드를 추가한다.

#### 이 제약으로 검증되는 것과 안 되는 것

이 전략은 **개장 갭**을 먹는다. 09:11은 개장 11분 뒤이고, 그때의 호가·거래량·갭
분포는 09:00:00과 다른 국면이다. 따라서 개발 트리의 라이브 실행은:

- **검증된다** — 주문 전송·정정·취소 경로, 체결 폴링, F4 추적, F5 청산, 상태
  저장과 재시작 복구, 잔고·체결 조회 응답 처리. 요컨대 **주문 경로의 동작**.
- **검증되지 않는다** — F1 선정 품질, 갭 가드 판정, 진입가의 타당성. 요컨대
  **전략 자체**. 09:11의 후보는 09:00의 후보가 아니다.

이건 우회할 수 있는 제약이 아니라 **의도된 분업**이다. 개장 창을 두 프로세스가
나눠 쓸 방법은 없다(레이트 제한 하나, 계좌 하나). 전략 검증은 하위 프로젝트 B의
재생이 맡는다 — 재생은 그날 09:00:00에 실제로 기록된 응답을 쓰므로 국면이
정확하고, 장 시간과 무관하게 아무 때나 반복할 수 있다.

**개발 트리의 라이브 실행 결과를 전략 판단의 근거로 쓰면 안 된다.** 이 구분이
흐려지면 09:11 표본으로 개장 전략을 판정하게 된다.

### 계좌 단위 스크립트 차단

`scripts/paper_close_all.py`는 계좌 전체를 청산한다. `.stock-role`이 `prod`가
아니면 거부한다.

### 해결되지 않는 것

같은 앱키를 쓰므로 KIS 초당 1건 제한은 계속 공유한다. 시간 분리(개발 09:11 이후)로
개장 창의 경합만 피할 뿐이다. 15:15 청산 시각에는 양쪽 F5가 동시에 돌 수 있으므로,
개발 청산 시각을 뒤로 미루거나 개발이 그 전에 정리해야 한다.

## 6-5. 운영 모드별 적용 범위

운영이 REAL로 전환되면 계좌·URL이 분리된다. 공유에서 오는 규칙은 해제되지만,
**앱키에서 오는 규칙은 남는다.**

2026-09-10 확인 결과 `.env.paper`와 `.env.real`의 `KIS_APP_KEY`가 동일하다
(URL만 다르다). `.env.real`이 아직 실전용으로 채워지지 않은 복사본으로 보인다.
따라서 REAL 전환 시 앱키를 분리할지 여부가 아래 표의 마지막 두 줄을 가른다.

| 규칙 | 운영 PAPER | 운영 REAL (앱키 공유) | 운영 REAL (앱키 분리) |
|---|---|---|---|
| 예산 분할 0.70/0.30 | 적용 | **미적용** | **미적용** |
| 종목 충돌 회피 | 적용 | 미적용 (계좌 분리) | 미적용 |
| 개발 09:11 이후 | 적용 | **유지** (레이트 공유) | 해제 가능 |
| 토큰 캐시 공유 | 적용 | **금지** (토큰 상이) | 금지 |

### 예산 — REAL 전환 시

"비율 미적용"은 운영이 0.95로 돌아간다는 뜻이 **아니다.** REAL에는 별도 정책이
이미 있다 — `readiness.py`의 `initial_allocation` 게이트가 `0 < F3_ALLOC_RATIO
<= 0.20`을 요구한다. 실전 초기 투입은 20% 이하다.

정확히는 이렇다.

- 운영(REAL): 개발 분할과 무관하게 REAL 자체 정책값(초기 0.20 이하)을 쓴다
- 개발(PAPER): 모의계좌를 단독으로 쓰므로 분할 전 값(0.95)으로 복귀한다

### 토큰 — REAL 전환 시 반드시 분리

5절의 `AUTH_DIR` 공유는 **양쪽이 모두 PAPER일 때만 성립한다.** REAL 토큰과 PAPER
토큰은 발급 호스트가 달라 서로 쓸 수 없다. 운영이 REAL이 되면 개발은 자기
`AUTH_DIR`을 갖고 PAPER 토큰을 직접 발급해야 하며, `KIS_AUTH_READONLY`를 꺼야
한다.

앱키가 공유된 상태라면 이때 두 트리가 같은 앱키로 각각 토큰을 발급하게 된다.
그 조합의 안전성은 미확인이다 — REAL 전환 전에 실측하거나, 앱키를 분리한다.

### 전환 절차에 남길 것

위 조정은 잊기 쉽고 잊으면 실전에서 드러난다. `docs/REAL_TRADING_CHECKLIST.md`에
항목으로 넣는다.

1. 운영 `F3_ALLOC_RATIO`를 REAL 정책값(초기 0.20 이하)으로 변경
2. 개발 `F3_ALLOC_RATIO`를 0.95로 복귀
3. 개발 `AUTH_DIR`을 자기 트리로 되돌리고 `KIS_AUTH_READONLY=0`
4. `DEV_EXCLUDE_HELD_TICKERS` 해제 (선택 — 켜둬도 무해)
5. 앱키 분리 여부 결정. 분리하면 개발 스케줄 오버라이드(09:11)도 해제 가능

## 7. 이 변경 자체의 지문 비용

3절의 기준을 이 작업에 적용하면 마이그레이션은 **2단 배포**다.

| 변경 | 지문 영향 |
|---|---|
| `.stock-role`, `promote.ps1`, `preflight.ps1`, 런처 검사 | 없음 |
| `paper_close_all.py` 가드 | 없음 |
| 보유종목 제외 플래그 (`f3_entry.py`) | 바뀜 |
| 스케줄 env 오버라이드 (`schedule_times.py`) | 바뀜 |
| `F3_ALLOC_RATIO` 0.95 → 0.70 | 바뀜 |

셋을 **하나의 릴리스로 묶어 지문을 한 번만 바꾼다.**

### 묶기의 시한

2026-09-10의 `PAPER_FAST_HYBRID` 전환은 아직 운영에 반영되지 않았다. 환경변수는
기동 시 읽히고 워치독이 매일 08:00~10:01 창에서 프로세스를 새로 띄우므로,
**2026-09-11 08:00 기동에서 `833edca5fff4`가 활성화된다.**

그 전에 이 릴리스를 함께 올리면 리셋이 한 번으로 끝난다. 놓치면 두 번이다
(`833edca5fff4` 0건 시작 → 마이그레이션 릴리스에서 다시 0건 시작).

시한을 놓치는 것 자체는 사고가 아니다. 잃는 것은 거래일 며칠 치 증거뿐이고,
서두르다 마이그레이션을 그르치는 쪽이 훨씬 비싸다. 준비가 안 됐으면 두 번 리셋을
받아들이는 것이 맞다.

## 8. 마이그레이션

```
1. D:\Private\stock-prod 로 clone, 릴리스 태그 체크아웃
2. data\ 복사 (2026-09-10 기준 59.6MB / 300파일) — 원본은 개발 트리에 남김
3. .venv 재생성 (pip install -r requirements.txt)
4. .env / .env.paper / .env.real 복사 후 운영값 조정 (F3_ALLOC_RATIO=0.70)
5. .gitignore에 .stock-role 추가 (트리별 파일이므로 추적하지 않는다)
6. .stock-role 생성 — prod / dev 각각
7. 개발 트리 .env 조정 — UI_PORT=8898, F3_ALLOC_RATIO=0.30,
   AUTH_DIR·REPLAY_SOURCE_DIR을 운영 경로로, KIS_AUTH_READONLY=1
8. Task Scheduler 2건(StockBot_Watchdog / StockBot_Backfill) 경로를 stock-prod로
9. 개발 트리 data\ 정리 — 운영 이력은 지우고 빈 디렉터리로 시작
```

`.gitignore` 항목 추가는 5번이지만 실제로는 릴리스 커밋에 포함돼야 한다 — 운영
트리가 태그를 체크아웃한 시점에 이미 무시 규칙이 있어야 워킹트리가 더티해지지
않는다.

### 검증

- 운영 수동 기동 정상, 개발 기동 정상, 두 UI 동시 접속
- 개발에서 `KIS_MODE=REAL` 시도 → 거부
- 개발이 토큰 캐시를 읽기만 하고 운영 토큰이 유효하게 유지되는가
- 운영 트리에서 파일 수정 → 다음 기동 거부
- `promote.ps1`을 개발 트리에서 실행 → 거부
- `paper_close_all.py`를 개발 트리에서 실행 → 거부

### 롤백

개발 트리에 모든 것이 그대로 남아 있다. Task Scheduler 경로를 되돌리고
`stock-prod`를 지우면 원상복구된다.

## 9. 후속

하위 프로젝트 B(과거 날짜 재생 하네스)는 별도 스펙으로 진행한다. 기존 조각
(`replay_ticks_to_bars.py`, `strategy_backtest.py`, `fast_path_counterfactual.py`)이
파이프라인의 한 계층씩만 재현하고 F1→F5 전 구간을 통으로 도는 것이 없다. B는
"새로 만들기"가 아니라 "조각 통합 + 빈 구간 채우기"에 가깝다.

B는 편의 기능이 아니다. A가 개발 트리에 남긴 공백 — 09:11 제약 때문에 전략을
검증할 수 없다는 것(6절) — 을 메우는 것이 B의 존재 이유다. A만으로는 주문 경로만
확인할 수 있고, 전략 변경은 여전히 근거 없이 운영에 올라간다.

B가 완성되면 이 스펙 3절의 2단 게이트에서 "재생 검증 결과"가 선택 항목에서 필수
항목으로 바뀐다.
