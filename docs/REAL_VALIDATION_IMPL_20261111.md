# 실전 검증 게이트 구현 보고 (1차 — 경로·정책값과 무관한 부분)

작성일: 2026-11-11 · 브랜치 `hichang4u/real-validation` (기준 `0727069`, main과 같은 커밋)

**2차 검토로 바뀐 것이 있다.** 이 보고의 3절 '해석 8가지'와 예약·증거 설명 일부는
`docs/REAL_VALIDATION_PREPARATION.md`(검토 발견 9건, 절차 권고, 정책 초안)가 대체한다.
아래 본문은 1차 시점의 기록으로 남긴다.

상태: **독립 모듈·판정 규칙·준비도 게이트 연결까지 구현, 합성 자료로만 검증.**
PAPER 60거래일 수집, REAL 실측, 스모크, 승격은 하지 않았다. 여기서 "통과"는 테스트가
통과했다는 뜻이지 수익성·경로·위험 검증이 통과했다는 뜻이 아니다.

기준 설계: `docs/REAL_VALIDATION_DESIGN.md` (부모 `main`의 미커밋 파일, SHA-256
`e57f142b…551a47`). 이 브랜치에는 그 설계 문서 4개를 **커밋하지 않았다** — 부모 트리의
미커밋 변경이라 소유가 다르다. 워크트리에 사본만 두고 기준으로 삼았다.

## 1. 결론

- REAL 신규 진입 자격이 **여섯 조건의 AND**가 됐다. 준비도 100점은 그중 하나다.
  지금 코드로는 어떤 설정으로도 `eligible_for_real=true`가 나오지 않는다(§5의 차단 3가지).
- 전략 지문 대상 파일은 하나도 건드리지 않았다. **20건 카운터는 그대로다.**
- 매수 경로(f3_entry) 연결, 위험 한도 감시의 런타임 호출, 실행 경로 선택은 하지 않았다.
  전부 전략 파일 변경이거나 사용자 결정이라 남겼다(§7).

조사 중 확인한 사실 둘:

1. **REAL 호환 호가 신선도를 PAPER에 적용할 수 없다.** `f3_entry`는 PAPER에서
   `F3_FINAL_QUOTE_MAX_AGE_MS`를 1,500ms 아래로 내려도 1,500ms로 올려 쓴다. 호가 나이
   501~1,500ms에서 PAPER는 진입하고 REAL은 막는다(`scripts/execution_mode_diff.py` 실행
   결과, 8개 입력 중 3개 불일치). 설계 §6-5 "REAL 호환 설정을 PAPER에 적용"은 이 한 항목
   때문에 설정만으로는 안 되고 전략 변경이 필요하다. REST 호출 간격(1.1초/0.2초)과 빠른
   경로(PAPER 전용)도 모드에 따라 다르다.
2. **현재 20건 카운트는 어느 경로를 골라도 REAL까지 못 간다.** 준비도는
   `PAPER_FAST_PROBE/HYBRID` 꺼짐을 요구하는데 트랙 A는 2026-09-11부터 빠른 경로 구간이다
   (`src/perf_costs.py` 구간표, 운영 `.env`는 열지 않았다). 기존 경로를 고르면 그 환경변수가,
   빠른 경로를 고르면 코드가 바뀌어 지문이 바뀐다.

## 3. 구현 단위

전부 새 패키지 `src/real_validation/`(지문 비대상)이다. I/O는 `store.py`와 `gate.py`의
파일 읽기뿐이고 나머지는 순수 계산이다.

| 파일 | 우선순위 | 내용 |
|---|---|---|
| `core.py` | P1 | 판정값, 정규화 해시(`db._canonical_config_hash`와 같은 규약), 시각 파싱 |
| `store.py` | P1·P3 | 추가 전용 SQLite. 등록·증거·중단·예약 네 테이블, UPDATE/DELETE 트리거 차단 |
| `evidence.py` | P1 | 증거 참조 8종, 만료, 낡은 증거 판정, 실험당 최종 판정 1회 |
| `profitability.py` | P1 | 잠금 미래 검증 판정식과 판정 |
| `gate.py` | P1 | AND 게이트, `REAL_VALIDATION_DIR` 읽기 전용 평가 |
| `execution_profile.py` | P2 | 실행 계약·프로필 id, 재생 비교, 지연 요약, 환경 차이 판정 |
| `costs.py` | P3 | 비용 정책 버전, 실제 순손익, 스트레스 손익 |
| `risk_policy.py` | P3 | 필수 정책값과 유효성(미정·0=무제한·20% 상한·손절 폭만의 스트레스) |
| `sizing.py` | P3 | 허용 금액·수량, 미체결 예산 예약/해제 |
| `risk_halt.py` | P3 | 지속 중단, 해제 절차, 한도 판단, 매수 외 행동 허용 |

기존 파일 변경은 `src/readiness.py` 하나다(지문 비대상). `percent`·`groups`는 그대로이고
`operational_ready`·`real_gate`가 추가됐으며 `eligible_for_real`이 AND 결과가 됐다.
`blockers`에는 게이트 차단 사유가 덧붙는다 — `main`의 `REAL_START_BLOCKED` 로그와
대시보드가 이 목록을 그대로 쓴다.

`scripts/execution_mode_diff.py`는 현재 코드의 모드 차이를 읽기 전용으로 열거한다
(주문·시세 호출·DB 없음).

### 차단을 기본값으로 둔 곳

- 사전등록값·정책값·프로필 항목은 전부 `None`이 기본이고 `None`은 미정 → 차단이다.
  코드에 임계값 기본값을 넣지 않았다. 설계가 고정한 값만 상수다(60거래일 하한, 95%,
  투입비율 20% 상한).
- 0은 무제한으로 읽지 않는다(`*_ZERO_MEANS_UNLIMITED`).
- 설정 파일의 모르는 키는 거부한다. 오타로 한도 하나가 사라진 채 통과하지 않게 한다.
- 저장소가 없거나 깨졌으면 '중단 아님'이 아니라 '확인 불가'로 본다. 읽는 쪽은 저장소를
  만들지 않는다.
- 판정일 전에는 신뢰구간을 계산하지 않는다. 판정 뒤에는 판정일까지의 자료만 쓴다.
- 한 실험의 최종 판정은 한 번만 기록된다. 다시 판정하려 하면 통계를 내기 전에 거부한다.

### 설계가 열어 둔 곳에서 내가 고른 해석 (확인 필요)

숫자가 아니라 절차다. 모두 더 엄격한 쪽을 골랐고 `EVALUATION_RULE_VERSION`에 묶여 있다.

1. 불리 시나리오에서도 평균뿐 아니라 MDD·CVaR·연속손실 한도를 요구한다.
2. 경계: 한도는 '이내' 통과(값=한도 통과), 양수 조건은 0 초과, 손실 중단은 손실=한도에서 발동.
3. 판정식은 수집 시작일 **전날까지** 잠가야 한다(당일 장전 잠금도 거부).
4. 블록 bootstrap은 무거래일을 포함한 거래일 달력의 원형 블록 재표집, 하한은 nearest-rank.
   표본이 빈 재표집의 평균은 0으로 센다.
5. 탐색 구간 자료가 입력에 섞여 있으면 걸러내지 않고 판정 자체를 거부한다.
6. 미해결 포지션이 있으면 `INSUFFICIENT`.
7. CVaR 표본 부족 시 처리는 `BLOCK`만 받는다.
8. 미체결 예약 금액은 현금 한도에서도 뺀다(증권사 주문가능금액과 이중으로 빠질 수 있다).

## 5. 지금 REAL이 차단되는 이유 (의도된 상태)

1. `REAL_VALIDATION_DIR` 미설정 → 다섯 항목 `NOT_EVALUATED`. 운영 PAPER는 이 상태이고
   파일을 하나도 읽지 않는다.
2. 정책·증거가 전부 있어도 `gate.PRE_BUY_ENFORCEMENT_WIRED = False`라
   `risk_policy_valid`가 통과하지 않는다. 주문 직전 예산 확인이 매수 경로에 없는데 한도를
   믿을 수는 없다. 이 값은 매수 경로를 연결하는 릴리스가 바꾼다.
3. 기존 조건(정상 청산 20회, 승인 플래그 3종 등)은 그대로 남아 있다.

REAL 1주 스모크(`allow_real_smoke_buy`) 경로는 건드리지 않았고 자격·표본으로 쓰이지 않는다.
