# 텔레그램 알림 1건 유실, 무엇이 사라졌는지 로그로 알 수 없다 — 후속 티켓 (2026-10-26)

2026-10-26 09:00:27에 텔레그램 알림 한 건이 세 번 다 실패로 기록되고 버려졌다. 매매에는 영향이 없다. 로그에
오류 내용도 알림 종류도 없어서 어떤 알림인지 사후에 가릴 수 없었다.

**정정 (2026-10-26, 사용자 확인).** 사용자는 HT로보틱스 **매수 체결 알림을 3번**, 매도 체결 알림을 1번 받았다.
사라진 알림은 없었고, 매수 체결 알림이 시도마다 도착해 **3번 중복**됐다. 응답만 5초 안에 오지 않아(타임아웃)
코드가 실패로 보고 다시 보낸 것으로 보인다(추정 — 예외 종류가 기록되지 않았다). 아래 1 ~ 4절의 "유실"은
"전송 확인 실패"로 읽는다.

## 2. 증거

`src/notifier.py` `worker()` (131 ~ 161행).
- 한 알림을 최대 3회 보낸다. 시도마다 `httpx.AsyncClient(timeout=5)`이다.
- 예외가 세 번 나면 `log("NOTIFICATION_FAILED", level="WARN", error=str(e))`만 남기고 다음 알림으로 넘어간다.
  - httpx의 타임아웃 예외(`ReadTimeout` 등)는 `str(e)`가 빈 문자열인 경우가 있다. 이날 로그에 `error`가 없는 것과
    맞는다(추정, 예외 종류는 기록되지 않았다).
  - 알림 본문이나 종류는 기록하지 않는다.
- 응답이 429면 `retry_after`만큼 쉬고 다시 보낸다. **그 밖의 응답(400, 5xx 등)은 성공과 똑같이 `break`한다.**
  상태 코드를 보지 않으므로 이런 실패는 로그 없이 사라진다.

운영 로그 95일(2026-06-24 ~ 10-26)에서 `NOTIFICATION_FAILED`가 있는 날 (실측):

| 날짜 | 시각 | `error` |
|---|---|---|
| 0702 | 09:27:02 · 04 · 05 | `All connection attempts failed` (3건) |
| 0901 | 08:30:58 · 08:56:10 | `[Errno 11001] getaddrinfo failed` (DNS) |
| 0901 | 08:57:11 | (빈 값) |
| 1026 | 09:00:27 | (빈 값) |

- 빈 값은 0901에도 한 번 있었다.
- 429 외 오류 응답으로 버려진 알림은 로그가 없어 셀 수 없다.

## 3. 원인 (확정 안 됨)

- 같은 1 ~ 2초 동안 KIS 주문·조회 API도 평소보다 2 ~ 5배 느렸다. 개장 직후 이 PC나 회선의 외부 통신이 함께
  느렸을 수 있다(추정). 텔레그램 쪽 지연인지는 가를 증거가 없다.
- 0901은 DNS 실패였다. 같은 무렵 WS·REST 장애 티켓(`docs/WS_REST_OUTAGE_FOLLOWUP_20261021.md` 6절, 10/22)에도
  우리 쪽 DNS 실패 기록이 있다. 같은 원인인지는 모른다.

## 4. 영향

- **매매: 없음.** 알림은 매매 판단 경로가 아니다. 이날 진입·청산은 정상이었다.
- **운영 감시:** 사라진 것이 진입 체결 알림이었다면, 사용자는 그 진입을 대시보드나 청산 알림에서야 알게 된다.
  알림이 사라졌다는 사실도 로그를 열어야만 보인다.
- **사후 분석:** 어떤 알림이 사라졌는지, 왜 실패했는지 로그로 가릴 수 없다.

## 5. 선택지 (결정 전)

`src/notifier.py`는 지문 대상이 아니다(CLAUDE.md). 무엇을 골라도 실계좌 카운터에 영향이 없다.

- **가. 그대로 둔다.** 95일 중 3일, 매매 영향 없음.
- **나. 실패 기록을 보강한다.** `error=repr(e)`(예외 종류 포함), 알림 첫 줄(어떤 알림인지), 시도 횟수를 남긴다.
  429 외 오류 응답도 상태 코드와 응답 첫 부분을 `NOTIFICATION_FAILED`로 남긴다. 기록만 늘어난다.
- **다. 나에 더해 버리지 않는다.** 세 번 실패한 알림을 큐 뒤에 다시 넣거나, 간격을 늘려 몇 번 더 보낸다. 늦게라도
  도착한다. 장애가 길면 같은 알림이 쌓이므로 상한이 필요하다.
- **라. 나에 더해 유실을 다음 알림에 붙인다.** 다음에 전송이 성공할 때 "앞선 알림 N건 전송 실패" 한 줄을
  덧붙인다. 사용자가 로그를 열지 않아도 유실을 안다.

## 6. 중복 (정정으로 드러난 것)

- 텔레그램 `sendMessage`에는 중복 방지 키가 없다. 요청은 닿았는데 응답이 늦으면, 다시 보낼 때마다 같은 알림이
  한 번 더 간다. 10/26 매수 체결 알림 3번이 그 결과로 보인다(추정).
- 선택지 추가 (결정 전):
  - **마. 응답 타임아웃(`ReadTimeout`)은 다시 보내지 않는다.** 연결 자체가 안 된 경우(`ConnectError`·
    `ConnectTimeout`)만 다시 보낸다. 중복은 없어지지만, 요청이 실제로 닿지 않은 타임아웃이면 그 알림은 사라진다
    (라의 안내 줄로만 알게 된다).
  - **바. 응답 대기 시간을 늘린다.** 5초 → 10초 등. 중복이 줄지만 큐 뒤 알림이 그만큼 늦는다.
  - **사. 그대로 둔다.** 중복이 유실보다 낫다고 본다.

## 7. 결정 (2026-10-26)

나·라를 채택했다(`src/notifier.py` `_deliver`). 재시도 횟수·간격과 중복 동작은 그대로다(6절 마 ~ 사는 열려 있다).
- `NOTIFICATION_FAILED`에 `alert`(제목·종목), `attempts`, `errors`(시도별 예외 종류), `error`(마지막 예외 repr),
  `status`·`body`(오류 응답), `delivery`(`REJECTED` = 서버가 거부, `UNCONFIRMED` = 응답 없음 — 도착·중복 가능)를
  남긴다. 429가 3번 이어진 경우도 기록한다(전에는 로그 없이 끝났다). 봇 토큰은 `***`로 가린다.
- 실패한 알림은 다음에 전송이 성공하는 알림 끝에 "※ 앞선 알림 N건 전송 확인 안 됨: …"으로 붙는다(3건까지
  이름, 나머지는 "외 N건"). 붙여 보낸 뒤 `NOTIFICATION_UNCONFIRMED_REPORTED`(`count`)를 남기고 목록을 비운다.

### 8.2 증거

- **알림 요청은 한 번이다.** 마감 청산 알림을 큐에 넣는 곳은 `src/modules/f5_timeout.py` 418행 한 곳이고,

- **보내는 곳이 하나다.** 운영 `main.py` 프로세스는 하나다(2026-10-27 15:52 승격분). 텔레그램 토큰을 읽는 코드는
  `src/notifier.py`뿐이다. 15:20 이후 예약 작업(`StockBot_OvernightScreen1520`·`OvernightScreen`·`Backfill`·
  `Watchdog`)은 notifier를 쓰지 않는다.
- **재시도 뒤 성공은 기록되지 않는다.** `_deliver`는 예외가 나면 다시 보낸다. 2회차나 3회차에 성공하면 시도별
  예외(`errors`)를 버리고 `True`만 돌려준다. 7절의 기록은 세 번 다 실패했을 때만 남는다.

  있다(추정).
